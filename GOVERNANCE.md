# Governance

iSystem OS uses a maintainer-led governance model during public beta. The goal is fast, transparent decisions without implying a mature foundation or formal membership structure.

## Roles

- **Contributors** propose issues, documentation, code, tests, and reviews.
- **Reviewers** provide trusted review in an area but do not merge by role alone.
- **Maintainers** triage, set direction, merge changes, manage releases, and enforce community and security policies.

Current repository ownership is represented in `.github/CODEOWNERS`. Code ownership indicates review responsibility, not exclusive copyright ownership.

## Decisions

Routine changes are decided through pull-request review. Changes to architecture, data compatibility, licensing, trademarks, governance, or security boundaries require a public proposal with rationale and maintainer approval. Security-sensitive details may be discussed privately until coordinated disclosure.

Maintainers seek rough consensus. When consensus is not possible, the repository owner makes the decision and records the rationale publicly when safe.

## Becoming a maintainer

Maintainers may invite contributors who demonstrate sustained, constructive work; sound technical judgment; respect for security and privacy; and reliable review. There is no application quota or guaranteed timeline. Access follows least privilege and can be removed for inactivity, risk, or policy violations.

## Releases

A maintainer verifies the release checklist, resolves licensing and notice blockers, reviews changes, and publishes releases. Automation may assist but must not replace approval. Beta releases may contain breaking changes and must state known limitations.

## Changes to governance

Propose changes by pull request. Material changes should remain open long enough for community review unless an urgent security or legal issue requires immediate action.
